# برومبت شامل — تخطيط تطوير نظام محاسبي تجاري (ERP-Lite)

> **موجّه إلى Claude Code.** هذا المستند نتيجة جلسة تخطيط كاملة تمت مع صاحب المشروع (مطوّر .NET Full-Stack). كل القرارات أدناه مُثبَّتة ومحسومة. **المطلوب منك في هذه المرحلة: إعداد خطة تطوير تفصيلية فقط — لا تكتب أي كود فعلي بعد.**

---

## 0. السياق العام

مطلوب بناء نظام محاسبي تجاري (ERP-Lite) يُباع كمنتج لعدة عملاء (شركات)، وليس نظاماً داخلياً لشركة واحدة. صاحب المشروع مبرمج (خبرة عميقة بـ ASP.NET Core/EF Core، وخبرة أقل بـ Node.js)، وليس محاسباً، والمتطلبات المحاسبية أدناه صيغت بمساعدة استشارة محاسبية أثناء التخطيط. **كل الكود سيُكتب عبر أدوات AI (أنت)، وليس يدوياً من صاحب المشروع** — هذا قرار مؤثر على اختيار التقنيات أدناه (أولوية لـ type-safety وبنية واضحة تقلل احتمالية الأخطاء الصامتة).

## 1. السوق المستهدف وحجم العملاء

- **السوق الأساسي**: المملكة العربية السعودية + دول خليجية أخرى (الإمارات، عُمان مستقبلاً).
- **حجم الشركات المستهدفة**: مرن — يجب أن يخدم شركات صغيرة ومتوسطة وكبيرة بدون نسخة منفصلة لكل حجم.
- **طبيعة النشاط**: عام وشامل، غير مقيّد بصناعة واحدة (تجارة/توزيع بشكل أساسي حالياً، مع إمكانية توسّع لاحقاً لتصنيع/تجزئة).
- **نموذج النشر**: **On-Premise / Single-tenant** — نسخة منفصلة كاملة تُنشر عند كل عميل على بنيته التحتية الخاصة، وليس SaaS متعدد المستأجرين.
- **اللغة والواجهة**: عربي وإنجليزي معاً من أول يوم (دعم RTL و LTR كامل، وليس ترجمة لاحقة).

## 2. قرار حرِج: حماية الترخيص (License Protection)

بما أن النشر On-Premise والمنتج يُباع تجارياً، **يجب** أن تتضمن الخطة آلية ترخيص/تفعيل (License Key + Activation) تمنع نسخ النظام وتشغيله بدون تفعيل صالح. هذا قرار معماري يجب تصميمه من البداية (مثلاً طبقة Middleware في الـ API تتحقق من صلاحية الترخيص عند كل تشغيل، مع دعم تفعيل أونلاين دوري أو offline لمرة واحدة — الآلية بالتفصيل مفتوحة، اقترح تصميماً مبدئياً ضمن خطتك).

## 3. متطلبات الامتثال الضريبي (حرِج جداً — لا مجال للتأجيل)

### 3.1 السعودية (ZATCA / فاتورة) — إلزامي وفعلي حالياً
- نظام "فاتورة" التابع لهيئة الزكاة والضريبة والجمارك (ZATCA) إلزامي لكل الشركات المسجلة بضريبة القيمة المضافة.
- المرحلة الثانية (التكامل) تُطبَّق على موجات حسب حجم الإيرادات: الشركات فوق 750 ألف ريال إيرادات خاضعة للضريبة يجب أن تتكامل مع منصة فاتورة قبل 31 مارس 2026، وفوق 375 ألف ريال قبل 30 يونيو 2026 — وستستمر الموجات لتشمل شركات أصغر تباعاً.
- **متطلبات تقنية**: توليد فاتورة إلكترونية بصيغة XML (معيار UBL 2.1)، ختم تشفيري (Cryptographic Stamp)، رمز QR بترميز TLV، وربط API مباشر مع منصة فاتورة.
- فواتير B2B وB2G: يجب أن تمر بـ"تخليص" (Clearance) لحظي مع ZATCA قبل اعتبارها صالحة قانونياً — الفاتورة بدون تخليص لا قيمة ضريبية لها ولا يمكن للمشتري خصم ضريبة المدخلات عليها.
- فواتير B2C: تُبلَّغ (Reporting) لـ ZATCA خلال 24 ساعة من الإصدار.
- أرشفة إلزامية لكل الفواتير (UUID، Hash، ملف XML) لمدة 10 سنوات كحد أدنى.
- كل عميل يحتاج عملية "Onboarding" أولية تربط نسخته بحساب فاتورة الخاص به على منصة ZATCA.

#### 3.1.1 توضيح مؤكد: لا حاجة لشركة وسيطة — الربط المباشر ممكن ومسموح

- ZATCA لا تفرض قائمة "معتمدة" إلزامية لمزودي الحلول. أي شركة (Taxpayer) يحق لها تختار أي حل يحقق الاشتراطات التقنية، **حتى لو مطوّره غير مدرج** بقائمة ZATCA "الإرشادية" لمزودي الحلول المنشورة على موقعها — تلك القائمة اختيارية/تعريفية فقط وليست شرط امتثال.
- **الأهم**: ZATCA لا تعتمد "العلامة التجارية" للبرنامج ولا تمنح شهادة عامة لمطوّر البرنامج؛ هي تعتمد **كل نشر (Deployment) على حدة، مرتبطاً برقم ضريبي واحد (TIN)**. يعني كل عميل يشتري البرنامج لازم يمر بعملية Onboarding خاصة فيه هو (وليس عملية تسجّلها إنت كمزوّد برنامج مرة واحدة لكل عملائك):
  1. تسجيل دخول العميل على بوابة فاتورة (Fatoora Portal) بحسابه الخاص وتوليد OTP.
  2. توليد Certificate Signing Request (CSR) من داخل النظام وإرساله لـ ZATCA عبر الـ API.
  3. استلام Compliance CSID (شهادة مؤقتة للاختبار).
  4. اجتياز اختبار Sandbox (حد أدنى 10 فواتير تغطي: فاتورة قياسية، إشعار دائن، إشعار مدين، فاتورة مبسّطة — ضمن 12 سيناريو اختبار إلزامي).
  5. طلب واستلام Production CSID (الشهادة النهائية، صالحة لمدة سنة وتحتاج تجديد).
- **عملياً — طريقان متاحان، وكلاهما لا يحتاج شركة وسيطة إلزامية:**
  - **مباشر بالكامل (موصى به لبنية Core+Modules الحالية)**: تبني منطق التوقيع الرقمي (ECDSA) وتوليد XML (UBL 2.1) والـ QR (TLV) وسلسلة الـ Hash بنفسك داخل `Modules.Compliance.ZATCA`، وتتصل مباشرة بـ API الخاص بـ ZATCA لكل عميل. يعطيك استقلالية كاملة وبدون أي تكلفة متكررة لطرف ثالث، لكنه يتطلب تعاملاً دقيقاً مع مكتبات التشفير والامتثال الكامل للمواصفة التقنية.
  - **بديل اختياري (أسرع تطويراً)**: الاعتماد على مزوّد "Compliance Middleware" جاهز (مثل Complyance أو مزودين مشابهين) يتولى عنك تعقيد التوقيع والـ XML وCSID، وتتصل ببرنامجك على API أبسط تبعه. أسرع بالتطوير، لكن بتكلفة اشتراك/رسوم متكررة تنعكس على تسعيرك لكل عميل، وتصبح معتمداً على طرف ثالث تشغيلياً.
- **الأثر المباشر على `Modules.Compliance.ZATCA`** (بافتراض المسار المباشر): يجب أن يتضمن (1) واجهة "معالج ربط" (Onboarding Wizard) لكل عميل جديد تنفّذ الخطوات الخمس أعلاه، (2) منطق توليد/توقيع XML وQR وHash Chain، (3) اختبار تلقائي داخلي يغطي سيناريوهات ZATCA الإلزامية قبل طلب Production CSID.

### 3.2 دول خليجية أخرى (للتخطيط المستقبلي فقط — ليست ضمن النطاق الحالي)
- **الإمارات**: تتبنى نموذج Peppol (5-corner model عبر مزودي خدمة معتمدين) — مختلف تماماً عن النموذج المركزي السعودي. بدأ التفعيل التدريجي بالإمارات.
- **عُمان**: تتبنى نموذج Peppol مشابه للإمارات، مع شمول B2B وB2G وB2C من البداية.
- **قطر/البحرين/الكويت**: لا يوجد إلزام ناضج بعد — لا حاجة لبناء دعم لها الآن.

### 3.3 الأثر التصميمي الإلزامي
**module الامتثال الضريبي يجب أن يكون Plug-in منفصل تماماً (واجهة موحّدة + تطبيق مختلف لكل دولة)**، وليس كوداً مدمجاً داخل منطق الفوترة العام. هذا يسمح ببيع النظام بالسعودية الآن بحزمة ZATCA فقط، وإضافة حزمة الإمارات لاحقاً دون المساس بباقي النظام.

## 4. المعمارية العامة: Core + Modules + Compliance Packs

النمط المعماري: **Modular Monolith** (وليس Microservices — لا مبرر لتعقيد الشبكة والنشر بحجم نسخة واحدة لكل عميل).

```
Solution / Monorepo
├── core/                    (النواة الثابتة — لا تتغير حسب نوع العميل)
├── modules/
│   ├── inventory/
│   ├── purchasing/
│   ├── sales/
│   └── compliance-zatca/
├── api/                     (يجمّع كل الموديولات ويعرضها كـ API واحد)
└── web/                     (React frontend)
```

### 4.1 النواة (Core) — المكوّنات الثابتة
- دليل حسابات شجري (Chart of Accounts) قابل للتخصيص.
- محرك ترحيل محاسبي (Accounting/Posting Engine) — القيد المزدوج التلقائي.
- إدارة شركات وفروع متعددة، عملات متعددة وأسعار صرف.
- نظام صلاحيات مركزي على مستوى الشاشة/الإجراء.
- سير موافقات قابل للتهيئة (Configurable Approval Workflows).
- سجل تدقيق كامل (Audit Trail) لكل عملية إضافة/تعديل/حذف.
- مولّد ترقيم مستندات مركزي وقابل للتهيئة لكل عميل.
- التقارير المالية الأساسية: ميزانية عمومية، قائمة دخل، تدفقات نقدية.

### 4.2 قواعد ثابتة لإضافة أي وحدة (Module) جديدة — عقود التكامل الخمسة

**كل موديول، حالي أو مستقبلي، يجب أن يلتزم بهذه النقاط الخمس ولا يبني منطقه الخاص بها:**

1. **محرك الترحيل المحاسبي الموحّد (`IAccountingEngine`)** — الموديول لا يكتب قيوداً مباشرة لقاعدة البيانات؛ يطلب من النواة ترحيل العملية.
2. **نظام الصلاحيات المركزي (`IPermissionService`)** — نفس الأدوار والمستخدمين المعرّفين بالنواة.
3. **نظام الترقيم الموحّد (`INumberingService`)** — أي مستند (فاتورة/أمر/سند) يأخذ رقمه من مولّد مركزي.
4. **سجل التدقيق المركزي (`IAuditLogger`)** — كل عملية تُسجَّل بنفس الآلية.
5. **طبقة التقارير الموحّدة** — بيانات الموديول تظهر بالتقارير المالية العامة، لا بتقرير معزول.

مثال توضيحي مبسّط (مفهوم فقط، ليس كوداً نهائياً) يوضح كيف يجب أن يعتمد أي موديول على واجهات النواة بدل تنفيذ منطقه بنفسه:

```typescript
// كل موديول يعتمد على خدمات النواة عبر Dependency Injection، ولا ينفّذ منطقها بنفسه
@Injectable()
export class PurchaseOrderService {
  constructor(
    private readonly accounting: IAccountingEngine,     // عقد 1: الترحيل المحاسبي
    private readonly permissions: IPermissionService,    // عقد 2: الصلاحيات
    private readonly numbering: INumberingService,        // عقد 3: الترقيم
    private readonly audit: IAuditLogger,                  // عقد 4: سجل التدقيق
  ) {}

  async create(userId: string, dto: CreatePurchaseOrderDto) {
    if (!this.permissions.canCreate(userId, 'PurchaseOrder')) {
      throw new ForbiddenException();
    }
    const orderNumber = await this.numbering.getNext('PurchaseOrder');
    // ... منطق إنشاء أمر الشراء الخاص بالموديول فقط ...
    await this.accounting.postEntry({
      debitAccount: 'المخزون',
      creditAccount: 'ذمم دائنة - الموردين',
      amount: dto.totalAmount,
      reference: orderNumber,
    });
    await this.audit.log(userId, 'PurchaseOrder', orderNumber, 'تم الإنشاء');
    return orderNumber;
  }
}
```

## 5. المتطلبات الوظيفية التفصيلية — الطبقة الأولى فقط (Tier 1)

### 5.1 المخزون
- طلب شراء داخلي من موظف المخزون، بحالة (معلّق / مُعالَج / مرفوض).
- ربط كل صنف بمستودع، وحد أدنى لإعادة الطلب (Reorder Point) مع تنبيه تلقائي.
- استلام أوامر الشراء وتحديث الكمية تلقائياً + توليد قيد محاسبي (زيادة المخزون).
- تقييم المخزون: **[مفتوح — FIFO أو متوسط مرجّح، يُحسم لاحقاً، صمّم الجدول بحيث يدعم الاثنين]**.
- تسويات جرد (الفرق بين الفعلي والدفتري).

### 5.2 المشتريات
- استلام طلبات الشراء من المخزون.
- اختيار المورد والسعر، مع إمكانية مقارنة أكثر من مورد لاحقاً.
- إنشاء أمر شراء رسمي (Purchase Order) مرتبط بالمورد والصنف والسعر.
- مسار موافقة اختياري فوق مبلغ معيّن قبل إرسال الأمر للمورد.
- عند الاستلام: مطابقة الكمية والسعر بين أمر الشراء والفاتورة الفعلية (3-way matching مبسّط) قبل الاعتماد النهائي.

### 5.3 المبيعات والذمم المدينة
- استقبال طلب العميل (يدوي حالياً) وإنشاء عرض سعر (Quotation) بالمنتجات والأسعار.
- تحويل عرض السعر إلى أمر بيع ثم فاتورة رسمية — **الفاتورة جزء من دورة النظام الكاملة، وليست PDF منفصل غير مرتبط بالمحاسبة**.
- الفاتورة الرسمية تمر عبر حزمة الامتثال (ZATCA) قبل اعتبارها نهائية.
- إرسال عرض السعر أو الفاتورة عبر البريد كـ PDF ثنائي اللغة (عربي/إنجليزي).
- متابعة التحصيل، كشف حساب العميل، وتقرير أعمار الديون (Aging Report).

### 5.4 حزمة الامتثال السعودية (ZATCA) — تفاصيل تقنية
(انظر القسم 3.1 أعلاه للمتطلبات القانونية الكاملة)
- توليد XML بمعيار UBL 2.1 + ختم تشفيري + QR بترميز TLV.
- تفرقة منطق B2B/B2G (Clearance لحظي) عن B2C (Reporting خلال 24 ساعة).
- أرشفة آمنة 10 سنوات كحد أدنى.
- عملية Onboarding أولية لكل عميل.

## 6. أولويات الإطلاق (Tiers)

- **الطبقة الأولى (إطلاق أول نسخة قابلة للبيع)**: النواة الكاملة + المخزون + المشتريات + المبيعات/الذمم المدينة + حزمة ZATCA. **هذا هو نطاق خطة التطوير المطلوبة منك الآن.**
- **الطبقة الثانية**: الذمم الدائنة الكاملة، الرواتب، الأصول الثابتة، نقاط البيع، حزمة الإمارات/عُمان.
- **الطبقة الثالثة**: التصنيع (BOM)، الميزانيات والتخطيط المالي، تقارير BI متقدمة، تكاملات خارجية.

## 8. المطلوب منك تحديداً الآن (Claude Code)

بناءً على كل ما سبق، أعدّ **خطة تطوير تفصيلية فقط (لا تكتب كوداً فعلياً بعد)** تغطي:

1. **بنية المشروع الكاملة** (Monorepo/Folder structure) لكل من الـ Backend (تقسيم NestJS Modules حسب القسم 4 أعلاه) والـ Frontend.
2. **تصميم أولي لقاعدة البيانات** (Prisma schema تصوري) للجداول الأساسية بالطبقة الأولى فقط (دليل الحسابات، القيود، المخزون، أوامر الشراء، عروض الأسعار/الفواتير، المستخدمين والصلاحيات).
3. **تصميم الـ API endpoints** الأساسية لكل موديول بالطبقة الأولى.
4. **خطة مراحل تنفيذ (Milestones)** مرتبة منطقياً (مثال: النواة أولاً → المخزون → المشتريات → المبيعات → دمج ZATCA).
5. **خطة Docker Compose** التفصيلية (الخدمات، الشبكات، الـ volumes، متغيرات البيئة).
6. **تصميم مبدئي لآلية الترخيص/التفعيل** (القسم 2 أعلاه).
7. **قائمة بكل الافتراضات التي اتخذتها** وأي أسئلة تحتاج إجابة قبل بدء التنفيذ الفعلي.

**التزم بصرامة بـ:**
- نمط Modular Monolith وعقود التكامل الخمسة لأي موديول.
- عدم كتابة كود فعلي — هذه مرحلة تخطيط فقط.
- عدم اقتراح تقنيات بديلة عن القسم 7 — الـ Stack محسوم نهائياً.

## 9. نقاط مفتوحة (اذكرها كـ"قرارات معلّقة" في خطتك، لا تفترض حلاً نهائياً لها)

- نموذج التسعير النهائي (اشتراك / حسب الوحدات / ترخيص لمرة واحدة).
- طريقة تقييم المخزون (FIFO أو متوسط مرجّح).
